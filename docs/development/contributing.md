# Contributing

Start with the package that owns the behavior: `packages/core` owns crate input,
resource safety and diagnostics; `packages/validator` owns BIA validation and
browser sessions. Package behavior tests live under the corresponding package's
`tests/`. Repository-level `tests/` contains cross-package, browser, parity and
installed-consumer checks. See [architecture and contributor path](architecture.md)
and [package ownership](workspaces.md) for boundaries and extension requirements.

## Local loop

Use Node 22 or 24, then run `npm ci`. Edit the owning TypeScript source and its
tests. Run the package's `npm test --workspace @bijux/ro-crate-core` or
`npm test --workspace @bijux/ro-crate-validator` for a focused check; build
first with `npm run build` when the tests depend on package output. Run
`npm run build` before `npm run check:types` on a fresh checkout: the editor
example resolves built package output. The typecheck covers the separate source,
test, browser and worker projects and generated-entry checks. `npm test` builds
and runs the ordinary local test suite. `npm run check:workspace` checks workspace metadata, dependency order and import boundaries.
The root `tsconfig.json` helps editors find projects; it is not the full check.

`make product-build` and `make product-types` provide the same build and
typecheck entry points without loading the shared Make framework. Run the build
first on a fresh checkout. Existing standards and CI targets remain available.

For the standalone authoring application, run `make app-dev` and open the
localhost address it prints. `make app-build` prepares the deployable server,
`make app-serve` builds and runs it, `make app-check` checks its source and
`make app-test` runs its focused tests. These commands build the workspace
packages first and do not start BSS. The Astro development command can run
in the background; stop it with `make app-stop`. Stop `make app-serve` with
Ctrl-C. See the
[application guide](creator-and-submission-app.md) for its capabilities and
optional reference fixtures.

Run `make docs-serve` to build the tracked Markdown and browse the local
documentation at <http://127.0.0.1:4173/>. Set `DOCS_PORT` to use another
port; stop the server with Ctrl-C. `make docs-build` prepares the site under
`artifacts/documentation/site` without starting a server. Python 3 is needed
only for serving. Add new Markdown to Git before building so it is included.

Use `npm run test:parity -- --snapshot` for snapshot compatibility checks.
Independent live parity requires the pinned Python reference environment; browser
and release qualification require additional tools. The README gives setup and
commands, and [validation checks](validation-checks.md),
[compatibility evidence](../compatibility/PARITY.md) and the
[release procedure](release.md) explain the broader checks and prerequisites.
CI also exercises installed archives, browsers and independent reference results;
a passing focused local test does not replace those checks.

On POSIX, managed reference commands use a dedicated process group. A timeout
remains a failure after graceful shutdown; the group owner escalates if needed
and checks for live group members before reporting cleanup. A lost owner or an
unavailable process listing makes cleanup unconfirmed. Descendants that start a
separate session are outside this guarantee. Windows reference execution does
not yet provide an independently tested process-tree cleanup guarantee.

## Generated files and review

Package implementation and public types are authored in TypeScript. The build
emits JavaScript and declarations into each package's ignored `dist/`; do not edit
those outputs. Checked-in runtime entries carry a generated banner naming their
`.mts` source and generation command. Edit that source, then run
`npm run generate:runtime` (or `npm run generate:admission` for the admission
entry). Commit the resulting entries with the source. `npm run check:types`
checks that registered entries are current. They exist for direct execution on
supported Node 22 releases, including admission before dependency restoration.

The runtime entry inventory in `scripts/runtime-entries.mts` owns both generated
files and their `.gitattributes` review markers. When adding, moving or removing
an entry, update the inventory and run `npm run generate:runtime`; do not mark
handwritten JavaScript as generated by extension. Review the authored source
and inspect the generated diff when necessary.
Other generated data and reference captures have their own provenance and
regeneration instructions in the relevant compatibility documentation. Managed
shared standards follow [standards adoption](standards-adoption.md).

A pull request should describe the behavior and evidence, include relevant tests
and generated entries, and record the change in the repository changelog with
its pull request link once available. Report checks run and any prerequisites or
checks that were unavailable.

Root Node test selection is audited with `npm run check:test-selection`. Run
`npm run test:tooling -- --test-name-pattern "pattern"` for tooling and CI
contracts after building the packages. For one file, use
`node --import tsx --test path/to/file.test.ts`. The selection audit does not
replace the separate browser, reference or parity qualification checks.

Tooling contracts are grouped under `tests/tooling/` by responsibility, such as
`build/`, `workspaces/`, `reference/` and `packages/`. Workflow scheduling and
admission contracts remain under `tests/ci/`.

Direct metadata model tests mostly live under `packages/validator/tests/metadata/models/`;
`metadata/model-type-diagnostics.test.ts` also exercises the model validator.
RDF tests live under `packages/validator/tests/metadata/rdf/`. For example,
run `node --import tsx --test packages/validator/tests/metadata/models/dates.test.ts`
after building the packages.

## Common changes

For a validator rule, locate its owner under `packages/validator/src/` and its
matching tests under `packages/validator/tests/`. After `npm ci` and
`npm run build`, run the relevant file, for example
`node --import tsx --test packages/validator/tests/metadata/models/dates.test.ts`.
Run the validator workspace suite and `npm run check:types` for the broader
local check. Behavioral changes that affect reference compatibility also need
the parity and independent-reference checks described in
[validation checks](validation-checks.md).

For repository tooling, edit its owning `.mts` source under `scripts/` or
`tests/`, together with the corresponding test under `tests/tooling/` or
`tests/ci/`. After `npm ci`, run `npm run generate:runtime` when the source has
a registered runtime entry, then run `npm run build` and the relevant test,
for example `node --import tsx --test tests/tooling/boundaries.test.ts`. Run
`npm run check:types`, `npm run check:workspace` and
`npm run check:test-selection` when those contracts are affected.

For an installed-consumer failure, start with `npm ci` and `npm run build`, then
run `node scripts/release/pack.mjs` and `node tests/package/consumers.mjs --prepare`.
The latter creates the installed consumers and proof under `artifacts/consumers/`.
Run `node tests/package/consumers.mjs --verify` to check the prepared contents,
or `BIJUX_TEST_NODE=24.3.0 node tests/package/consumers.mjs --node` under the
matching Node version to reproduce the Node scenario. Browser scenarios need
the Playwright setup in the README; inspect the reports in `artifacts/reports/`.
Run the full package and browser qualification for release evidence; a single
local scenario is diagnostic rather than a replacement for the hosted matrix.
